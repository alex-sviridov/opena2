# Map coverage (phase K0)

What stands between each original map and full playability, so the rest of phase K is ordered by data. Regenerate with

```sh
.venv/bin/python -m engine coverage            # out/coverage.csv (map x feature, gitignored) and the block below
```

The block between the markers is generated; the text before and after it is written by hand (K0, 2026-11-09) and quotes the numbers of that run.
Code and the status table: `engine/coverage.py` (`FEATURES`, `STEPS`; the trigger kinds are probed from the trigger code itself). Tests:
`tests/test_engine_coverage.py`. A K step that builds a feature flips its status in `engine/coverage.py` in the same change and ends by running the
command (CLAUDE.md, session routine).

**How a map is judged.** The scan reads only the map data: the check / instant / group kinds that an *active trigger reaches*, the usable structures
(`Usable` in structures.reg, split by editor name), the structures a script reads (check 21, instant 26), the quest items a check waits for that a
monster carries or a sack holds, the spells on unit types and items, shooters, casters, flyers, music zones. A feature is a **blocker** only where the
data shows the mission's goal passes through it (checked by hand for the ones found: the quest-item triggers feed the variables that end the mission,
the switch checks are the puzzle of maps 93-96 and 103, a signpost instant is always a message). The smoke run (1600 ticks, script and AI, no player)
adds what the engine itself reports. It found one crash (map 96, a cast at a 2 x 2 target; fixed in the same commit, `tests/test_engine_spells_cast.py`).

### 4. Order, with reasons

1. **`campaign` spine first.** It is the only step that changes what is *inside* the maps (the party, its items, the recruits, the two variable-gated branches), it is fully
   headless, the objective run is its test driver (chain all missions in unlock order, report the party's level and the result per map), and every later step needs its state:
   the shell starts it, the town screens edit it, a save serialises it. It also answers whether the fresh-party decision matters (the six idle-lost maps).
2. **`shell` second.** With the spine the campaign can be played from the first map in one window; this is the first step after which you can play more than map 32 without a command line.
3. **`town` third.** The loop between missions (world map, hero screen, shops) is the largest and most REA-heavy piece; it needs the spine's state and the shell's windows.
4. **`save` fourth.** It is only useful once there is something worth saving (the campaign and its town state); the format is a decision for you (below).
5. **`cutscenes` last.** Independent of everything, no map and no state depends on it.
- In parallel, and not a step: your play-through of map 32 and the playability check of the maps, then the VERIFY BY EAR list (audio.md). They produce the only evidence the engine cannot give itself.

**Decision for you (not blocking L1-L3):** `save` as an own format (replay-based or a world dump: cheap, our files only) or as the original `game%d.sav` (compatible, needs the open server-stream research).
