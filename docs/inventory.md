# Install inventory and binary triage

Survey of `samples/Allods2_en_251005/Allods2_en/` (English 1.30, allods2.eu
build). The task asked for `samples/game/`, but that path does not exist, so
this install was used instead. The install shipped with an empty `maps/`.
On 2026-10-15 the 216 `.alm` maps from the allods2.eu maps pack
(`https://allods2.eu/files/maps_all.zip`) were added there. The per-file list (path, size, extension,
first 16 bytes) is generated by `tools/inventory.py` into `out/inventory.csv`.
That file stays in the gitignored `out/` directory because it contains bytes
taken from the game files.

```sh
python3 tools/inventory.py            # -> out/inventory.csv (5,299 rows)
```

Markers: **CONFIRMED** means checked in the binary via REA (routine address
given) or validated against every file in the install. **INFERRED** means
anything else.

### Assets the exe references that this install does not ship

These are CONFIRMED as strings in `allods2.exe`. None of them exist on disk
(maps did not either until the maps pack was added):

- **`.res` archives**: `cs.res`, `main.res`, `patch.res`, `world.res`,
  `music.res`, `video.res`, `movies.res`, `scenario.res`, `speech.res`, `sfx.res`
  (table at 0x5fd13c). a2mgr adds `locale.res`. This install keeps the
  contents as loose files under `data/` instead (INFERRED, see §4).
- **Campaign missions**: `%d.alm` and `World\Mission\scr_` (INFERRED to live
  inside `world.res`/`scenario.res`). The maps pack supplies `maps/*.alm` but
  not these numbered mission files.
- **Music**: `music\B00..B16.wav`, `menu.wav`, `map.wav`, `chrgen.wav`,
  `credit.wav`. a2mgr also looks for `data\music`.
- **Video**: `video\%s\%02d.smk`, `video\logos\nival.smk`. Only the `.reg`
  companions ship.
- **Characters and saves**: `chr\%s\%u%u.a2c`, `game%d.sav` (a2c are written at runtime).
- **Network packers**: `Packer1.dat`, `Packer2.dat`, referenced from 0x509ca3
  next to "CBufferManager::ReceiveData(). Error during unpacking buffer".
  They are compression tables for net traffic (INFERRED).

Getting a retail install, or another source of `.res` files and the
campaign missions, is the main data gap.

### scenario.dll

`ScenarioNewGame/Load/Save/GetVar/SetVar/TalkTo/EnterInn/EnterShop/EnterLocation/…`
make up the single-player campaign state machine. `ScenarioLoad` (0x10003686,
CONFIRMED via REA) reads from the save stream through a vtable `Read`
(+0x3c) in this order:

1. a 0x1000-byte variable block
2. 4 × 4 records of 0x14 bytes
3. a u32 count N, then N list entries
4. a u32 cursor

## 4. a2mgr.dll (allods2.eu client patch)

- **Online updater** (CONFIRMED strings): it fetches `/allods/version` and
  `/allods/version_id` from `api.allods2.eu` and posts `action=check_version`
  with checksums of the exe and dll. It keeps `allods2.exe.old` and
  `a2mgr.dll.old`, and stages updates as `data/allods2.exe` and `data/a2mgr.dll`.
- **`data/version`** is that manifest: `<path relative to data/> <sha1>`, 5,075
  lines, append-only. 5,072 entries match the files on disk. The 3 that
  don't are older hashes of the exe and dll, which are listed several times. I
  checked this with SHA-1 over every listed file. The format is CONFIRMED by
  data; that the last entry wins is INFERRED. `data/version_id` holds the
  40-hex SHA-1 of the manifest set (INFERRED).
- **Loose-file override** (INFERRED from strings `data\`, `data\patch\`,
  `locale.res`, `world\data\*`, `data\%s%d.256`, `data\%s%d.png`): Ordinal_108
  and friends map `.res` paths onto `data/`, which is why this install has no
  `.res`. The `%s%d.png` path lets PNG replace `.256` for numbered
  sprites. The equipment directories hold 516 PNGs whose IDs **never overlap**
  the `.256` IDs, so they are items added after release.
- Also UI in PNG/TTF via GDI+, screenshot upload, chat (`hat.allods2.eu`), and
  a log written to `allods2.log`.

## 5. Custom formats: what is known

### 5.1 `.reg` registry (`&YA1`)

The header is CONFIRMED by FUN_004ed6cc (allods2.exe). The size equation
also holds for all 17 files.

| Offset | Size | Field |
|---|---|---|
| 0x00 | u32 | signature 0x31415926 (`26 59 41 31`), else throws "bad signature" |
| 0x04 | u32 | ? (0 in all files) |
| 0x08 | u32 | ? (1…194; top-level entry count, INFERRED) |
| 0x0c | u32 | ? (always 0x11) |
| 0x10 | u32 | N = number of 32-byte directory entries |
| 0x14 | u32 | ? (0 in all files) |
| 0x18 | N × 32 | directory entries, see below |
| … | u32 | D = data blob size |
| … | D | data blob (strings / arrays referenced by entries, INFERRED) |

The check is `0x18 + 32·N + 4 + D == file size` for all 17 files.

Directory entry, 32 bytes. Found while reading `projectiles.reg` for
[lighting](mechanics/lighting.md). The layout is INFERRED, but consistent on
all 17 files (every section and blob range is in bounds) and gives
meaningful values; it has not been checked in the exe yet:

| Offset | Size | Field |
|---|---|---|
| +0 | u32 | 0 |
| +4 | 8 | value: a union by type (below) |
| +12 | u32 | type |
| +16 | char[16] | name, NUL-padded |

| Type | Count (all files) | Value at +4 / +8 |
|---|---:|---|
| 1 section | 513 | first child entry index, child count |
| 2 int | 5,025 | i32 value |
| 0 string | 1,770 | blob offset, length (cp1251, NUL-terminated) |
| 4 float | 22 | f64 (e.g. `startfade`, `endfade` in `video/*/NN.reg`) |
| 6 int array | 444 | blob offset, byte length of u32s (e.g. `AnimationTime`, `AnimationFrame`) |

The first `header[0x08]` entries are the top-level sections: 32 in
`projectiles.reg`, namely `Global` and `Projectile0`–`Projectile30`. The value
0x31415926 also appears in FUN_004eae80, FUN_004ed9f0 and FUN_004edd03
(writers or other readers, INFERRED). The same container probably backs
`.res` archives as well (INFERRED, unverified).

### 5.2 `.alm` maps (`M7R\0`)

216 files, 32,596–386,478 bytes. 210 distinct contents (6 are byte-identical
copies under other names). The container below is CONFIRMED by data: walking
it ends exactly at EOF for all 216 files. Field meanings are INFERRED; nothing
here has been checked in the exe yet.

File header, 20 bytes:

| Offset | Size | Field |
|---|---|---|
| 0x00 | 4 | magic `M7R\0` |
| 0x04 | u32 | header size, always 0x14 |
| 0x08 | u32 | always `width·height·4 + 72` (all 216) |
| 0x0c | u32 | section count, always 13 |
| 0x10 | u32 | always 0x640 (1600) |

Then 13 sections, each with a 20-byte header `{u32 tag, u32 header size
(0x14), u32 data size, u32 id, u32 ?}` followed by the data. The tag is 7 in
212 files and 5 in 4 files (`aeq_maraslavin_1_104R`, `sc_ac_necro_1_2`,
`sc_acq_zwilling_1_1`, `sc_acq_zwilling_1_11`), perhaps a version.
**Quirk:** section 0 is followed by 16 bytes beyond its declared size (644).
Section IDs always appear in the order 0, 1, 2, 3, 5, 11, 4, 9, 8, 6, 7, 10, 12.

| ID | Size | Observations |
|---|---|---|
| 0 | 644 (+16) | General info. u32 width, height at data +0x00 / +0x04 (file 0x28 / 0x2c): 144² (101), 80² (46), 256² (38), 208² (13), plus non-square sizes from 48×112 to 256×144. Then at +0x08 f32 0x3f490fda (π/4) |
| 1 | w·h·2 | u16 per cell; terrain tiles |
| 2 | w·h | u8 per cell; heights |
| 3 | w·h | u8 per cell; object layer |
| 4–12 | variable | Records (structures, units, players, triggers, …, to be identified). Sections 8, 10 and 11 can be empty |

## 6. Plan: custom formats to reverse, in order

The order puts small, well-bounded formats first and those that many other
systems depend on before their dependants. Sprites, palettes and BMP are
already done.

1. **`.reg` registry: full entry and data-blob semantics.** Header is
   CONFIRMED. 17 test files, and it gates animation and metadata for units,
   structures, objects, projectiles, sfx and video. Start from FUN_004ed6cc
   and its callers, including the typed getters.
2. **Font metrics `fontN.dat`.** Trivial. Needed for any text rendering
   together with the done `.16` glyphs.
3. **Locale `.txt` conventions.** Trivial. Line-indexed vs `#key`/`<part>`
   files, cp1251. Needed by UI, items and quests.
4. **`world/data/data.bin`.** The core rules database (items, materials,
   classes, spells, units). Depends on nothing; almost every game system
   depends on it. Find the reader via the `Data.bin` string at 0x6072d4.
5. **`itemname.bin` / `itemname.pkt` / `itemex.txt`.** Small. They map
   item IDs to names and sprites and need the data.bin item model.
6. **`famehall.dat`.** Tiny and self-contained (low priority, quick win).
7. **`.res` archive container.** Not in this install but required to read a
   retail install. Probably the `&YA1` container (verify FUN_004edd03 /
   FUN_004eae80), so most of the work comes free after step 1. Needs a
   sample `.res` file.
8. **`.alm` maps.** The largest format: terrain, objects, units, triggers.
   It depends on data.bin, the `.reg` metadata (units, structures, objects) and
   terrain BMPs. Unblocked: 216 maps from the maps pack, and the container is
   already mapped out (§5.2). Strings: `%d.alm` (xref 0x492b02), "Map version
   too new". Sections 0–3 (header, tiles, heights, objects) could be
   done before data.bin, since only sections 4–12 need its IDs.
9. **`.a2c` characters / `game*.sav` saves** (including the scenario.dll save
   chunk from §3). These depend on the data.bin item and unit model, and on
   `.alm` for missions. a2c path built at 0x4f30b9.
10. ~~`human.pal` remap~~ Done: FUN_00425bee is the shade-table builder,
    and `human.pal` holds 16 player-colour palettes. See
    [palettes.md](formats/palettes.md).

Not planned as formats:

- `.smk` is standard Smacker and absent from this install.
- `Packer1/2.dat` and the network protocol belong to the network layer.
- `data/version` is already understood (§4).
